# Code of Conduct

## Our Commitment

DevOPs, including its Stratum subsystem in `stratum/`, is an open-source
technical project with high standards for both code quality and human
interaction. We are committed to making participation in this project a
respectful, professional experience for everyone.

---

## Standards

**Expected behavior:**

- Give and receive technical feedback directly and constructively
- Disagree on ideas, not on people
- Back assertions with evidence — benchmarks, papers, measurements
- Acknowledge when you're wrong; update your view when the evidence changes
- Respect that other contributors have different contexts and constraints
- Write ADRs when making significant decisions so reasoning is documented and revisitable

**Unacceptable behavior:**

- Personal attacks, insults, or harassment of any kind
- Dismissing contributions without technical justification
- Deliberately ignoring the documented rules in `AGENTS.md`, `CLAUDE.md` and `CONTRIBUTING.md`
- Claiming credit for others' work
- Publishing others' private information without consent

---

## Scope

This applies in all project spaces: GitHub issues, pull requests, code
reviews, discussions, and any other communication channel used for DevOPs or
Stratum development.

---

## Reporting

Report unacceptable behavior by opening an issue at
<https://github.com/MILTONADINA/DevOPs/issues>.

For a report that should not be public, use GitHub private vulnerability
reporting at <https://github.com/MILTONADINA/DevOPs/security/advisories/new>,
which only the maintainer can read. This works only after the repository
owner enables private vulnerability reporting in the repository settings
(see `docs/SECURITY.md`). Until then, open an issue that asks the maintainer
for a private channel, without including the details.

The maintainer reviews every report and keeps the identity of the reporter
confidential.

Responses may include: a warning, temporary suspension from participation, or
permanent removal from the project.

---

## Technical Disagreements

Technical disagreements are healthy and expected. The resolution process:

1. Both positions state their case with evidence (benchmarks, papers, code)
2. If unresolved: write competing ADRs and let the eval suite adjudicate where possible
3. If still unresolved: the maintainer makes a call, documents the decision, and moves on

Relitigating settled decisions without new evidence is not productive. If you
have new evidence that changes the calculus, open an issue referencing the
original ADR.
