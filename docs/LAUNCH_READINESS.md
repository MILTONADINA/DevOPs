### Stratum P0 — Known security caveat (Session 13 closure surfaced — RESOLVED Session 15 §2a-2)

**STATUS — RESOLVED 2026-05-28 (Session 15 v0.3.x §2a-2)**: capture-session.ts now consumes `redactValue` from `observability/pii-redaction.ts` and applies redaction to request.messages / system / tools / response.content BEFORE the capture artifact is written. **Surprise win during §2a-4 adversarial testing**: the 500KB-payload test revealed catastrophic backtracking in the email regex (`[a-zA-Z0-9._%+-]+@...` was O(N²) on long inputs without `@`). Hardened with an RFC-aligned bound on the email local-part {1,64} (RFC 5321) + domain {1,253} (RFC 1035), plus an 18-test dedicated unit-test file at `stratum/test/observability/pii-redaction.test.ts`.

**REDO correction (honest record)**: the original §2a-4 hardening ALSO bounded JWT segments {1,4096} and Bearer/sk-key {20,4096} "for consistency" — and that was a MISTAKE. The user-requested adversarial re-verification proved those upper bounds were **fail-OPEN**: a JWT with a segment >4096 chars failed the whole 3-segment match and the full token was written UNREDACTED to the capture artifact (sk-/Bearer left a raw overflow tail). Because `redactValue` returns normally on this false negative, the capture-session FAIL-CLOSED catch never fired. Remediated via **claim 098 (commit 113b697)**: an upper bound is the wrong tool for a literal-anchored, suffix-free greedy class (those are already linear); JWT is now `/eyJ[A-Za-z0-9._-]+/g` (one-pass, leak-free, linear) and Bearer/sk- use `{20,}`. Only email keeps a bound (no anchor + required `@…tld` suffix genuinely needs it; its bound leaks at most a few leading chars). +6 regression tests probe the >4096 leak direction + ReDoS linearity. Lesson: a green suite + 88.94% coverage HID this because no test exercised tokens past the upper bound — "coverage % + green" ≠ "secure". This is exactly what adversarial multi-agent verification is for.
